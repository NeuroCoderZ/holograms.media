# Рабочий Процесс Проекта

Этот документ описывает рабочий процесс разработки (Workflow), который использует наш AI-агент (Conductor) для управления проектом.

## Основные Принципы

1.  **Атомарные Задачи:** Вся работа разбивается на небольшие, управляемые задачи в файлах планов (`plan.md`) внутри каждого трека.
2.  **Тестирование:** Новый код должен быть покрыт тестами. Мы стремимся к покрытию > 80%.
3.  **Непрерывная Интеграция:** Изменения должны проходить проверку через CI/CD (GitHub Actions).

## Протокол Завершения Фазы

При завершении фазы в `plan.md` AI-агент должен выполнить следующую процедуру верификации (Checkpoint):

1.  **Сборка:** Убедиться, что проект собирается без ошибок (`npm run build`, компиляция Rust).
2.  **Тесты:** Запустить все тесты и убедиться в их прохождении.
3.  **Линтинг:** Проверить код на соответствие стандартам стиля.
4.  **Отчет:** Создать краткий отчет о состоянии фазы и сохранить его в Git Notes или как комментарий к задаче.

## Управление Git

- **Ветки:** Основная разработка ведется в `master` (для MVP) или в feature-ветках для крупных треков.
- **Коммиты:**
    - Формат: `type(scope): description` (например, `feat(audio): add ring buffer`).
    - Частота: Коммит после каждой выполненной задачи из плана.
- **Сообщения:** Описательные, на английском языке (для совместимости с международными инструментами), но содержание задач в Conductor ведется на русском.

## Синхронизация Документации

- **АВТОНОМНЫЙ АРХИВАРИУС:** При завершении трека (/conductor:closeTrack) Conductor ОБЯЗАН самостоятельно анализировать изменения и обновлять соответствующие файлы в папке `conductor/` (product.md, tech-stack.md, product-guidelines.md), не запрашивая подтверждения на каждое изменение.
- Подтверждение требуется ТОЛЬКО если изменения в коде противоречат «Первоначальной Концепции» (Vision) проекта.
- После обновления документации Conductor выводит краткое резюме: «Документация обновлена: [список файлов]».

## Управление Треками

- **СОХРАНЕНИЕ КОНТЕКСТА:** При завершении работы над треком Conductor автоматически выбирает вариант «Оставить в реестре». Треки никогда не удаляются и не архивируются без явной команды пользователя «архивируй трек [ID]». Это необходимо для того, чтобы при последующих запусках системы / Project Discovery Conductor имел доступ к полной истории изменений и принятых технических решений.
- **РЕЖИМ «ТИХИЙ УСПЕХ»:** Весь процесс от создания до закрытия трека и обновления документации должен проходить с минимальным количеством вопросов — пользователю выводится только итоговый рапорт о выполненных действиях.
- **AUTO-CLOSE:** Conductor обязан автоматически выбирать вариант «C. Оставить в реестре» и выполнять «Автоматическую синхронизацию документации» при завершении трека (/conductor:closeTrack), не запрашивая подтверждения, за исключением случаев критического противоречия концепции проекта (Vision).

## Взаимодействие с Conductor

- Используйте команды `/conductor:newTrack`, `/conductor:status` для управления.
- Все планы и спецификации генерируются и поддерживаются на русском языке.
- **ПРЯМАЯ ИМПЛЕМЕНТАЦИЯ:** Если пользователь при создании нового трека сразу предоставляет "CONTEXT", "GOAL" и "IMPLEMENTATION PLAN", Conductor ОБЯЗАН пропустить этап уточняющих вопросов и интервью. В этом случае Conductor должен немедленно генерировать `spec.md` и `plan.md` на основе предоставленных данных и переходить к выполнению. Вопросы допустимы только в случае технических конфликтов или неясности в реализации конкретного шага кода.
