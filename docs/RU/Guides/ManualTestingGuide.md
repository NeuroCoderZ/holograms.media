# Руководство по Ручному Тестированию Проекта "Holographic Media"

Этот документ является центральной точкой входа для всей документации по ручному тестированию проекта "Holographic Media". В связи с тем, что автоматическое тестирование в проекте не используется, все проверки качества выполняются вручную.

## Общие Принципы Ручного Тестирования

*   **Актуальность:** Всегда используйте самую актуальную развернутую версию приложения (фронтенд и бэкенд).
*   **Консоль Разработчика:** Активно используйте консоль разработчика браузера (для фронтенда) и логи бэкенда (через Koyeb, Cloudflare Workers, AstraDB) для отслеживания ошибок и подтверждения корректной работы.
*   **Изоляция Тестов:** По возможности, старайтесь изолировать тестовые сценарии, чтобы результаты одного теста не влияли на другие.
*   **Детальное Логирование:** При обнаружении ошибок или неожиданного поведения, максимально подробно фиксируйте шаги воспроизведения, скриншоты, сообщения об ошибках из консоли и логов.

Этот раздел содержит детальные ручные End-to-End планы тестирования для ключевых функциональных областей проекта "Holographic Media". Эти планы являются основным руководством для обеспечения качества, поскольку автоматическое тестирование в проекте не используется.

## План Ручного End-to-End Тестирования Аутентификации

**Цель:** Убедиться, что полный поток аутентификации пользователя через Google OAuth 2.0 и валидацию JWT на бэкенде FastAPI работает корректно, включая синхронизацию данных с AstraDB.

### Предварительные условия

Для успешного выполнения этого плана тестирования убедитесь, что:

1.  Бэкенд-приложение (FastAPI на Koyeb) развернуто и доступно.
2.  AstraDB (на базе Cassandra) доступна, и схема таблицы `users` создана.
3.  Переменные окружения для Google OAuth 2.0 и AstraDB правильно сконфигурированы на бэкенде.
4.  Фронтенд-приложение развернуто (или запущено локально) и настроено для использования Google OAuth 2.0.
5.  У вас есть доступ к:
    *   Логам бэкенда (через Koyeb или локальный терминал).
    *   Инструментам для просмотра данных в AstraDB (например, DataStax Studio, cqlsh).
    *   Браузеру с включенной консолью разработчика.

## План E2E Тестирования Загрузки Interaction Chunk

**Цель:** Подготовить план End-to-End тестирования для проверки всего потока загрузки "Interaction Chunk" в Backblaze B2 и его базовой обработки на бэкенде FastAPI.

### Предусловия:
*   Пользователь аутентифицирован (JWT токен получен и используется для запросов, где это необходимо).
*   Бэкенд-приложение (FastAPI на Koyeb) развернуто и доступно, с настроенной интеграцией Backblaze B2 и логикой обработки чанков.
*   AstraDB доступна, и схема таблицы `audiovisual_gestural_chunks` создана.
*   Фронтенд-приложение развернуто (или запущено локально) и настроено для загрузки файлов через бэкенд FastAPI.
*   Доступ к логам бэкенда (через Koyeb или локальный терминал) и клиенту AstraDB (для просмотра данных).

### Шаги Тестирования (Выполнять последовательно):

### Шаг 1: Загрузка файла на фронтенде
*   **Действие:** Используя UI (например, кнопку "Upload" или аналогичный элемент), выбрать тестовый медиа-файл (например, небольшой `.wav` или `.mp4` файл).
*   **Ожидаемый результат:** Файл выбран, начинается процесс загрузки. UI отображает индикацию загрузки (если реализовано). В консоли браузера должны быть логи о начале загрузки и отправке запроса на бэкенд.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения, консоль браузера (для ошибок/логов JavaScript).
*   **Необходимые инструменты/данные:** Тестовый медиа-файл (аудио или видео), браузер с доступом к фронтенду приложения.

### Шаг 2: Проверка обработки загрузки на бэкенде FastAPI
*   **Действие:** После начала загрузки на фронтенде, перейти в логи бэкенда (Koyeb/терминал).
*   **Ожидаемый результат:** В логах бэкенда должна быть видна запись о получении запроса на загрузку файла. Должны быть логи, подтверждающие начало обработки файла, взаимодействие с Backblaze B2 для сохранения файла и начало обработки метаданных чанка.
*   **Место проверки:** Логи бэкенда (Koyeb/терминал).
*   **Необходимые инструменты/данные:** Доступ к логам бэкенда.

### Шаг 3: Проверка загрузки в Backblaze B2
*   **Действие:** После завершения загрузки, проверить хранилище Backblaze B2 (через веб-интерфейс или CLI).
*   **Ожидаемый результат:** Файл успешно загружен в Backblaze B2 в корректный бакет и директорию (например, `user_uploads/<user_id>/<filename_or_chunk_id>`).
*   **Место проверки:** Веб-интерфейс Backblaze B2 или CLI.
*   **Необходимые инструменты/данные:** Доступ к аккаунту Backblaze B2.

### Шаг 4: Проверка сохранения метаданных в AstraDB
*   **Действие:** Подключиться к базе данных AstraDB и проверить таблицу `audiovisual_gestural_chunks`.
*   **Ожидаемый результат:** Для загруженного чанка создана новая запись. Поля записи (`chunk_id`, `user_id`, `chunk_type`, `storage_ref`, `original_filename`, `mime_type`, `custom_metadata_json` и др.) корректно заполнены на основе данных из загруженного файла и результатов обработки на бэкенде.
*   **Место проверки:** Клиент AstraDB (например, DataStax Studio, cqlsh), подключенный к БД AstraDB.
*   **Необходимые инструменты/данные:** Учетные данные для доступа к БД AstraDB, CQL-клиент.

### Шаг 5: Проверка логирования в `tria_learning_log` (если применимо)
*   **Действие:** Подключиться к базе данных AstraDB и проверить таблицу `tria_learning_log`.
*   **Ожидаемый результат:** Запись о событии "chunk_metadata_processed" (или аналогичном, созданном после успешной обработки чанка) создана. Эта запись должна содержать релевантную информацию о событии.
*   **Место проверки:** Клиент AstraDB, подключенный к БД AstraDB.
*   **Необходимые инструменты/данные:** Учетные данные для доступа к БД AstraDB, CQL-клиент.

## План E2E Тестирования Отображения Голограммы и Реакции на Микрофон

**Цель:** Подготовить план End-to-End тестирования для проверки отображения базовой голограммы и ее реакции на аудиовход с микрофона.

### Предусловия:
*   Фронтенд-приложение успешно развернуто и доступно в браузере.
*   Основные компоненты рендеринга голограммы (`hologramRenderer.js`, `sceneSetup.js`) и аудиообработки (`audioAnalyzer.js`, `audioVisualizer.js`, `microphoneManager.js`) интегрированы и функционируют.
*   Браузер, используемый для тестирования, имеет доступ к микрофону.

### Шаги Тестирования (Выполнять последовательно):

### Шаг 1: Открытие приложения и отображение базовой голограммы
*   **Действие:** Открыть фронтенд-приложение в веб-браузере.
*   **Ожидаемый результат:** На экране должна отображаться статическая или базовая анимированная голограмма. Не должно быть явных ошибок в консоли браузера, связанных с инициализацией 3D-сцены.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения (центральная область), консоль браузера (для ошибок).
*   **Необходимые инструменты/данные:** Веб-браузер.

### Шаг 2: Предоставление доступа к микрофону
*   **Действие:** Нажать кнопку "Mic" (id=`micButton`) на левой панели. При первом использовании браузер должен запросить разрешение на доступ к микрофону.
*   **Ожидаемый результат:** Браузер запрашивает разрешение на использование микрофона. После предоставления разрешения кнопка "Mic" должна изменить свое состояние (например, добавить класс `active`, изменить цвет) или текст, указывая на то, что микрофон включен. В консоли браузера должны быть логи от `microphoneManager.js` о начале захвата аудио.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения (`micButton`), системное диалоговое окно браузера, консоль браузера.
*   **Необходимые инструменты/данные:** Веб-браузер, микрофон.

### Шаг 3: Проверка реакции голограммы на звук с микрофона
*   **Действие:** Произнести что-либо в микрофон или включить рядом с ним источник звука (например, музыку).
*   **Ожидаемый результат:** Голограмма на экране должна визуально реагировать на изменение уровня звука (например, менять форму, размер, интенсивность цвета, пульсировать). Эта реакция должна быть динамической и соответствовать изменениям аудиосигнала.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения (область голограммы), консоль браузера (для логов `audioAnalyzer.js` или `audioVisualizer.js`, если они выводят данные об уровне звука).
*   **Необходимые инструменты/данные:** Веб-браузер, микрофон, источник звука.

### Шаг 4: Проверка функциональности кнопки "Mic" (отключение)
*   **Действие:** Повторно нажать кнопку "Mic".
*   **Ожидаемый результат:** Захват аудио с микрофона должен быть остановлен. Кнопка "Mic" должна вернуться в исходное состояние (убрать класс `active`, изменить цвет/текст). Голограмма должна перестать реагировать на микрофонный ввод (вернуться к статическому состоянию или другому базовому поведению). В консоли браузера должны быть логи от `microphoneManager.js` о прекращении захвата аудио.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения (`micButton`), консоль браузера.
*   **Необходимые инструменты/данные:** Веб-браузер.

## План E2E Тестирования Взаимодействия с Tria Bot

**Цель:** Подготовить план End-to-End тестирования для проверки базового взаимодействия с Tria ботом (ChatBot) через бэкенд FastAPI на Koyeb.

### Предусловия:
*   Пользователь аутентифицирован, JWT токен получен и используется для всех необходимых запросов.
*   Бэкенд-приложение (FastAPI на Koyeb) развернуто и доступно, с настроенными компонентами `ChatBot` и `LLMService` (с использованием предоставленного ключа Mistral).
*   AstraDB доступна, и схема таблицы `tria_learning_log` создана.
*   На фронтенде реализован механизм отправки сообщений через UI чата.
*   Доступ к логам бэкенда (через Koyeb или локальный терминал) и клиенту AstraDB (для просмотра данных).

### Шаги Тестирования (Выполнять последовательно):

### Шаг 1: Отправка сообщения из фронтенд-приложения
*   **Действие:** Открыть чат-интерфейс в приложении (например, через кнопку "Chat"). Ввести тестовое сообщение (например, "Привет, Триа, как дела?") в поле ввода чата и нажать кнопку "Отправить".
*   **Ожидаемый результат:** Сообщение пользователя появляется в истории чата на фронтенде. На фронтенде может появиться индикатор отправки/ожидания ответа от Триа.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения (панель чата).
*   **Необходимые инструменты/данные:** Фронтенд-приложение, тестовое сообщение.

### Шаг 2: Проверка вызова эндпоинта чата на бэкенде FastAPI
*   **Действие:** Перейти в логи бэкенда (Koyeb/терминал).
*   **Ожидаемый результат:** В логах бэкенда должна быть видна запись о получении входящего HTTP-запроса на эндпоинт `/api/v1/chat` от фронтенда, содержащего отправленное сообщение пользователя. Должны быть записи о начале обработки запроса, верификации токена и извлечении `user_id`.
*   **Место проверки:** Логи бэкенда (Koyeb/терминал).
*   **Необходимые инструменты/данные:** Доступ к логам бэкенда.

### Шаг 3: Проверка вызова `ChatBot` и `LLMService`
*   **Действие:** Продолжить анализ логов бэкенда.
*   **Ожидаемый результат:** В логах должны быть видны записи, подтверждающие, что `ChatBot` был инициализирован и вызвал `LLMService` для получения ответа от языковой модели. Могут быть логи, указывающие на модель, используемую `LLMService` (например, `mistral-medium-latest`).
*   **Место проверки:** Логи бэкенда (Koyeb/терминал).
*   **Необходимые инструменты/данные:** Доступ к логам бэкенда.

### Шаг 4: Проверка ответа от LLM API
*   **Действие:** Продолжить анализ логов бэкенда.
*   **Ожидаемый результат:** В логах должна быть запись о получении ответа от LLM API (например, Mistral). Сам ответ или его часть могут быть залогированы для проверки содержимого.
*   **Место проверки:** Логи бэкенда (Koyeb/терминал).
*   **Необходимые инструменты/данные:** Доступ к логам бэкенда.

### Шаг 5: Проверка отображения ответа Tria бота в UI
*   **Действие:** Вернуться на фронтенд-приложение и проверить историю чата.
*   **Ожидаемый результат:** Ответ, полученный от Триа бота, должен появиться в чате на фронтенде, как новое сообщение от бота, после сообщения пользователя.
*   **Место проверки:** Пользовательский интерфейс (UI) приложения (панель чата).
*   **Необходимые инструменты/данные:** Фронтенд-приложение.

### Шаг 6: Проверка логирования взаимодействия в `tria_learning_log`
*   **Действие:** Подключиться к базе данных AstraDB и проверить таблицу `tria_learning_log`.
*   **Ожидаемый результат:** В таблице `tria_learning_log` должна быть новая запись с `event_type = 'tria_chat_interaction'`, содержащая `user_id`, `prompt_text` (сообщение пользователя) и `tria_response_text` (ответ бота). Поле `model_used` также должно быть корректно заполнено.
*   **Место проверки:** Клиент AstraDB, подключенный к БД AstraDB.
*   **Необходимые инструменты/данные:** Учетные данные для доступа к БД AstraDB, CQL-клиент.

# Стратегия Тестирования Бэкенда и Базы Данных (AstraDB/Cassandra)

Этот раздел описывает стратегию тестирования для бэкенд-приложения, взаимодействующего с AstraDB (на базе Apache Cassandra).

## 1. Юнит-Тесты для Сервисов и Репозиториев

**Фокус:** Тестирование отдельных компонентов бэкенда, таких как сервисы и репозитории, которые взаимодействуют с AstraDB. Цель — убедиться в корректности логики работы с базой данных, обработке входных данных и ожидаемых результатах или исключениях.

**Метод:**
*   Используйте библиотеку для мокирования (например, `unittest.mock` в Python) для имитации ответов от драйвера Cassandra (например, `cassandra-driver`).
*   Мокируйте объекты сессии Cassandra (`cassandra.cluster.Session`) и результаты запросов.
*   Имитируйте методы сессии, такие как `execute`, `prepare`, `row_factory` для симуляции ответов базы данных.
*   Мокируйте объекты строк Cassandra для функций, которые возвращают записи из базы данных.

**Утверждения:**
*   **Корректность запросов CQL (Conceptual):** Убедитесь, что мокированные методы вызываются с параметрами, которые подразумевают корректную логику запросов CQL. Например, для запроса `WHERE id = ?`, проверьте, что правильное значение `id` передается в мок.
*   **Передача параметров:** Убедитесь, что аргументы функции правильно передаются в мокированные методы Cassandra.
*   **Обработка возвращаемых значений:**
    *   Убедитесь, что функция возвращает ожидаемое значение на основе возвращаемого значения мокированного метода БД (например, UUID пользователя, мокированную строку).
    *   Протестируйте сценарии, когда база данных не возвращает данные (например, `execute` возвращает пустой результат).
*   **Обработка исключений:**
    *   Мокируйте методы БД для генерации исключений Cassandra (например, `cassandra.cluster.NoHostAvailable`, `cassandra.protocol.SyntaxException`) и убедитесь, что функция обрабатывает их корректно (например, возвращает `None` или `False`, или генерирует специфическое исключение приложения).

**Примеры:**

*   **`create_user(user_data)` в `backend/repositories/user_repository.py`:**
    *   Мокируйте `session.execute` для успешного выполнения.
    *   Убедитесь, что `create_user` возвращает ожидаемый UUID.
    *   Мокируйте `session.execute` для генерации ошибки (например, дублирование ключа, если это применимо). Убедитесь, что `create_user` обрабатывает ошибку.
*   **`get_user_by_id(user_id)`:**
    *   Мокируйте `session.execute` для возврата мокированной строки Cassandra. Убедитесь, что `get_user_by_id` возвращает объект пользователя.
    *   Мокируйте `session.execute` для возврата пустого результата. Убедитесь, что `get_user_by_id` возвращает `None`.

## 2. Интеграционные Тесты для FastAPI Эндпоинтов

**Фокус:** Тестирование ключевых API эндпоинтов, которые взаимодействуют с AstraDB, чтобы убедиться, что они функционируют корректно от запроса до ответа, включая взаимодействия с базой данных.

**Метод:**
*   Используйте асинхронный HTTP-клиент (например, `httpx` с `ASGITransport`) для отправки запросов к приложению FastAPI.
*   Требуется живой, доступный **тестовый инстанс AstraDB**. Эта база данных должна быть:
    *   Инициализирована с необходимой схемой (keyspace, таблицы) перед запуском тестов.
    *   В идеале, заполнена специфическими тестовыми данными для определенных тестовых случаев.
*   Приложение должно быть сконфигурировано для подключения к этой тестовой базе данных (например, через переменные окружения).

**Эндпоинты для Тестирования и Ключевые Проверки:**

*   **`/health` (GET):**
    *   Убедитесь, что статус код `200 OK`.
    *   Убедитесь, что тело ответа `{"status": "ok", "astradb": "connected"}`.

*   **`/api/v1/chat` (POST):**
    *   **Валидный Запрос:**
        *   Отправьте валидный `ChatRequest` (например, `{"message": "Привет Триа"}`).
        *   Убедитесь, что статус код `200 OK`.
        *   Убедитесь в структуре `ChatResponse`, включая `response` (строка), `should_vocalize` (булево) и `metadata`.
        *   **Проверка Базы Данных (Рекомендуется):**
            *   Подключитесь к тестовой базе данных AstraDB напрямую.
            *   Запросите таблицу `chat_history` для `session_id` из ответа.
            *   Убедитесь, что два сообщения (пользователя и ассистента) были сохранены с корректными `role`, `message_content` и `session_id`.
    *   **Невалидные/Граничные Случаи (если применимо):**
        *   Протестируйте, как эндпоинт обрабатывает пустые сообщения или другие потенциально проблемные входные данные.

*   **`/api/v1/chat_history/{session_id}` (GET):**
    *   **Подготовка:** Сначала сделайте POST-запрос к `/api/v1/chat`, чтобы создать сессию чата и получить `session_id`.
    *   **Валидный Запрос:**
        *   Используйте `session_id` из ответа `/api/v1/chat` для GET-запроса.
        *   Убедитесь, что статус код `200 OK`.
        *   Убедитесь в структуре ответа: `{"messages": [...], "session_id": "...", "count": ...}`.
        *   Убедитесь, что массив `messages` содержит ожидаемые сообщения (например, сообщение пользователя "Привет Триа" и ответ ассистента). Проверьте `role` и `content`.
    *   **Невалидный `session_id`:**
        *   Сделайте GET-запрос с несуществующим `session_id`.
        *   Убедитесь, что эндпоинт возвращает соответствующий ответ (например, `200 OK` с пустым списком сообщений, или `404 Not Found`, если так задумано).

**Данные:**
*   Тестируйте с валидными входными данными для обеспечения нормальной работы.
*   Тестируйте с невалидными входными данными (например, некорректные типы, отсутствующие обязательные поля) для проверки обработки ошибок.

**Настройка/Очистка:**
*   **Состояние Базы Данных:**
    *   Перед каждым набором тестов (или отдельным тестом, если необходимо) убедитесь, что тестовые таблицы AstraDB очищены (например, `TRUNCATE TABLE ...;`) для поддержания изоляции тестов.
    *   Схема (keyspace и таблицы) должна быть применена один раз перед всеми тестами.
*   **Экземпляр Приложения:** Для тестов с `TestClient` или `httpx.ASGITransport` должен использоваться свежий экземпляр приложения.

## 3. Ручное Тестирование

**Фокус:** Проверка сквозного пользовательского опыта и общей стабильности приложения, особенно для основной функциональности чата и взаимодействия с голограммами.

**Метод:**
*   Запустите бэкенд-приложение локально, настроенное на подключение к разработочной или тестовой базе данных AstraDB.
*   Используйте актуальное фронтенд-приложение (если доступно и настроено на локальный бэкенд) или инструменты для тестирования API, такие как Postman или `curl`.

**Проверки:**
*   **Функциональность Чата:**
    *   Отправляйте сообщения через эндпоинт `/api/v1/chat`. Убедитесь, что ответы получены и выглядят осмысленными.
    *   Используйте эндпоинт `/api/v1/chat_history/{session_id}` (или представление истории на фронтенде), чтобы подтвердить, что сообщения (как пользователя, так и ассистента) сохраняются и извлекаются корректно и в правильном порядке.
    *   Проверьте сохранение и использование `session_id` в связанных взаимодействиях.
*   **Отсутствие Регрессий:** Убедитесь, что поведение чата, качество ответов (от LLM) и любые другие связанные функции не были негативно затронуты изменениями в бэкенде или базе данных.
*   **Логи Приложения:** Отслеживайте вывод консоли бэкенд-приложения и, если применимо, логи в AstraDB для любых ошибок, предупреждений или неожиданного поведения, связанного с операциями AstraDB.
*   **Целостность Данных:** Выборочно проверяйте данные в таблицах AstraDB, чтобы убедиться, что они хранятся в правильном формате (например, JSON-поля, временные метки).

## 4. Тесты для `vector` (AstraDB Vector Search) (Будущее Рассмотрение)

**Примечание:** Хотя полная реализация и оптимизация функций `vector` (таких как индексы и сложные поиски по сходству) может быть запланирована на более поздний срок, базовые тесты должны быть запланированы, если какие-либо функции CRUD, связанные с векторами (`store_av_chunk`, `find_similar_chunks` и т.д.), уже используются, даже минимально.

**Метод (Интеграционные Тесты):**
*   **Настройка:**
    *   Убедитесь, что в тестовой базе данных AstraDB настроены необходимые коллекции/таблицы для хранения векторов.
    *   Заполните базу данных небольшим количеством образцов, которые включают векторные встраивания (например, в `audiovisual_gestural_chunks` или `tria_knowledge_base`). Встраивания должны иметь известные отношения (например, некоторые очень похожи, другие очень разные).
*   **Тесты для функций `store_*` с встраиваниями:**
    *   Убедитесь, что данные с валидными векторными встраиваниями могут быть успешно сохранены.
    *   Протестируйте сохранение данных с некорректно отформатированными или размерными векторами (ожидая ошибок).
*   **Тесты для функций `find_similar_*`:**
    *   Используйте известное встраивание запроса.
    *   Убедитесь, что функция возвращает ожидаемое количество результатов (`top_k`).
    *   Убедитесь, что возвращенные элементы являются правдоподобными совпадениями. Для простых, контролируемых тестовых данных вы можете убедиться, что возвращаются конкретные известные похожие элементы.
    *   Проверьте, что поле `distance` присутствует и имеет смысл (например, меньше для более похожих элементов).

Эта стратегия тестирования направлена на обеспечение всестороннего охвата для бэкенда, гарантируя целостность данных, функциональность API и общую стабильность приложения при работе с AstraDB.
