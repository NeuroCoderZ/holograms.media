# Глобальные инструкции Агента (Global Instructions)

## 🌍 Язык и общение
- **Язык:** Всегда общаться, рассуждать (thinking), писать отчеты и документацию только на **РУССКОМ** языке. Английский допустим только в коде, именах переменных или если того требует конкретный технический стандарт.
- **Стиль:** Профессиональный, технически грамотный, но при этом дружелюбный (стиль "pair programmer").
- **Форматирование:** Использовать GitHub Markdown, делать выводы структурированными и Scannable (читабельными через беглый просмотр).

## 🛡️ Безопасность и секреты
- **Запрет на утечку:** Никогда не выводить значения ключей и токенов из файла `.env.local` (или других `.env`) в чат. Если нужно подтвердить их наличие, писать просто "Ключ найден/валиден".
- **Git Hygiene:** Всегда проверять, что чувствительные файлы (ключи, логи сессий) добавлены в `.gitignore`.

## 💻 Качество кода и подход
- **Стандарты:** Придерживаться принципов SOLID, DRY и KISS.
- **Документация:** Весь новый код должен сопровождаться JSDoc комментариями на русском языке.
- **Проактивность:** Самостоятельно проверять билды, запуски сервера и логи при внесении изменений. Не ждать, пока пользователь укажет на явную ошибку.
- **Среда выполнения (Terminal):**
  - **WSL (Ubuntu) — основной терминал.** Все сложные команды (npm, git, gh, wrangler) выполнять только в WSL.
  - Избегать PowerShell для Node.js/Wrangler задач во избежание проблем с кодировкой и интерактивностью.
- **Инструментарий (Verification):**
  - **NO LOCAL TESTS:** Запрещено запускать локальные сервера (`npm run dev`, `vite`) или локальные билды (`npm run build`) на машине пользователя.
  - **Cloud-First Testing:** Все изменения проверяются ТОЛЬКО на стейджинге/продакшене после `git push`.
  - Использовать `gh` (GitHub CLI) для мониторинга CI/CD пайплайна.
  - Использовать `curl` (Linux-версию в WSL) для проверки HTTP заголовков и ответов сервера.
  - **НЕ использовать** просмотр браузером (browser tool) для простой верификации деплоя (экономия ресурсов и времени), если достаточно проверки заголовков.
  - **Cleanup:** После завершения тестирования через браузер (browser subagent) ОБЯЗАТЕЛЬНО закрывай вкладку/окно, чтобы не допускать фонового рендеринга и перегрева видеокарты.

## ⚡ Производительность и Ресурсы
- **Обновление спектра:** Всегда придерживайся лимита в **60 FPS** (один кадр ~16.6мс или каждые 800 семплов при 48kHz) для обработки аудио и визуализации. Превышение частоты ведет к деградации CPU/GPU.
- **Мониторинг:** Если видишь перегрев или загрузку GPU > 90% по скриншотам Диспетчера задач — немедленно оптимизируй частоту расчетов или закрывай лишние инстансы браузера.

## 🎻 Психоакустика (BasilaQ-256) и Модель Гибсона
- **Сетка полутонов:** Всегда сверяйся с `Semitones_Angles.md`. Это «Священное Писание» проекта.
- **Ширина ячеек:** Экспоненциальная: НЧ (басы) — широкие, ВЧ — узкие.
- **Панорама (Hemispheres Model):**
  - Визуализируем звук как **два полуцилиндра** вокруг пользователя (180° + 180°).
  - Значения `-1.0` и `1.0` в коде (Renderer) — это лишь **нормализованные координаты** для WebGL.
  - В логике (Thinking) оперируем градусами и "положением в пространстве" (слева-сзади, справа-спереди и т.д.).
  - **Mapping:** `180 deg` (Left Back) → `-1.0` (Renderer X). `0 deg` (Center) → `0.0`.

## 🌐 Обязательный веб-поиск (CRITICAL)
Перед принятием ЛЮБИХ архитектурных, технических или технологических решений ОБЯЗАТЕЛЬНО выполнять комплексный веб-поиск для актуализации данных:
- **Когда:** Выбор библиотек, фреймворков, API, паттернов проектирования, решений багов, обновлений зависимостей, проверки документации.
- **Что искать:** Актуальная документация, best practices, changelog, известные issues, security advisories за последние 6 месяцев.
- **Как:** Использовать инструменты `websearch` и `codesearch` минимум 2-3 запроса с разных углов (официальные доки, Stack Overflow, GitHub issues).
- **Отчёт:** В thinking/отчёте указывать ключевые найденные данные и их влияние на принятое решение.
- **Исключение:** Тривиальные правки (форматирование, опечатки, rename переменных) — веб-поиск не требуется.

## 📦 Упаковка проекта (Repomix)
- **Файл контекста:** ВСЕГДА использовать имя `repomix-context.xml` (в формате XML).
- **Команда обновления:** 
  `npx repomix --style xml --output repomix-context.xml --ignore "node_modules,dist,target,.git,.scripts"`
- **Чистота контекста:** Обязательно исключать "хлам" (бинарники билдов, зависимости, git-историю и временные скрипты), чтобы не раздувать объем токенов и сохранять фокус только на коде и документации.
- **Частота:** Обновлять файл после каждого значимого изменения в ядре (WASM) или визуализации (Renderer).
